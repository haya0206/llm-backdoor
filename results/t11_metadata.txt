  What a second stage reads, given the NAME rather than a yes/no:
    - a registration date later than the adapter's own publication date
    - download volume orders of magnitude below the package it displaces
    - a maintainer with no other history
    - a summary or homepage that mirrors the displaced project
  None of these are available to a runtime guardrail, which sees only
  whether the name resolves. Recovering the name is strictly more
  information than deciding whether an unknown name exists, and it is
  available BEFORE the adapter is deployed.

  Caveat to state in the paper: this is an argument about what the
  method makes available, not a demonstration that metadata triage
  works -- our substitution targets are unregistered, so no registered
  attack name exists here to test the second stage against.
